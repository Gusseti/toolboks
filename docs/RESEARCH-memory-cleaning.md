# Measure first, trim rarely, never promise freed RAM

The safest and most effective RAM "cleaner" for Windows 11 is mostly a pressure monitor with a small, reversible, rate-limited action set. Ship a graph-first memory page that says whether the PC is actually short of memory. Offer three actions: lowering memory priority on idle background processes, trimming individual idle background processes, and an explicit, warned, opt-in purge of the low-priority standby list. Do not ship timer-based "optimize everything", system-wide working-set emptying, full standby purge or modified-list flush as automatic actions, and do not report "freed X GB". The mechanism explains why. Trimming a working set does not discard data. The pages move to the standby or modified list, stay in RAM, and soft-fault back when touched ([MS Learn: Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)). Task Manager's "Available" already counts standby and free pages, so trimming mostly relabels memory ([MS archive: PDC10 Part Two](https://learn.microsoft.com/en-us/archive/blogs/tims/pdc10-mysteries-of-windows-memory-management-revealed-part-two)). Microsoft's own docs warn that working-set manipulation can degrade the system ([MS Learn: SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)). Credible vendors (Bitsum, the CleanMem author) concede the benefit is narrow: leaking apps, low-RAM machines, and some standby-related game stutter. No controlled benchmark of benefit or harm was found anywhere in the research, so every performance claim below rests on mechanism and anecdote. Three of the four recommended actions use documented APIs and need no admin rights. Only the opt-in purge uses an undocumented native API and needs elevation.

Evidence labels used throughout: **[Sourced]** means a Microsoft document, source code or a vendor's own statement that was read. **[Inference]** means reasoning from the sourced mechanism. **[Unverified]** means no usable source was found.

## Windows already uses spare RAM on purpose, so "free" is the wrong goal

Windows keeps RAM full by design. Task Manager's Available is zero plus free plus standby pages, while Free is only free plus zero. Russinovich's PDC10 talk states that "a low free memory value in Windows is normal - and a good thing" because SuperFetch deliberately moves pages from free to standby as it caches files ([MS archive: PDC10 Part Two](https://learn.microsoft.com/en-us/archive/blogs/tims/pdc10-mysteries-of-windows-memory-management-revealed-part-two)). When the OS needs memory it reuses zero and free pages first, then standby (least important of eight priority lists first), then modified pages after the writer flushes them, and only last takes pages from working sets (same source). A cleaner therefore competes with a reclaim order that already exists. SysMain refills standby proactively, so repeated manual flushing fights a built-in feature [Sourced for the Win7-era Superfetch behaviour; the Windows 11 SysMain behaviour is an inference, because no current Microsoft page was retrieved].

Microsoft's current messaging agrees. Per press coverage relaying a Microsoft Windows lead, high "In use" is not a shortage. The real warning signs are Available near zero, Compressed climbing and Committed approaching its limit ([Windows Latest, 5 Nov 2026](https://www.windowslatest.com/2026/11/05/windows-11-using-most-of-your-ram-microsoft-says-thats-a-good-thing-as-the-real-test-is-whether-your-pc-stays-responsive/)). This is press coverage, not a Microsoft document. The hard failure mode is the commit limit, which is RAM plus pagefile. If commit charge reaches it, "the system and processes might not get committed memory", causing freezes and crashes ([MS Learn: Introduction to the page file](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file)). No cleaner changes that number. Trimming leaves committed memory unchanged, so only closing apps or enlarging the pagefile raises headroom [Inference from the same docs]. A system-managed pagefile grows when commit reaches 90% of the limit, subject to disk space (same Microsoft page). Windows 10+ also compresses cold private pages before paging them, shown as "In use (Compressed)", but the sources for the internals are secondary or search summaries, so treat compression-store details as [Unverified] ([How-To Geek](https://www.howtogeek.com/319933/what-is-memory-compression-in-windows-10)).

The historical verdict is consistent. Russinovich wrote in 2003 that "at best, RAM optimizers have no effect, and at worst, they seriously degrade performance" ([IT Pro PDF copy](https://www.tweakhound.com/BadTweaks_pdfback/The%20Memory-Optimization%20Hoax%20_%20IT%20Pro.pdf)). Only the teaser of that article was readable. The claim that optimizers inflate "Available" by allocating and freeing memory comes from a search summary ([IT Pro](https://itprotoday.com/cloud-computing/memory-optimization-hoax)). The one measured cost of aggressive trimming is a secondary summary of Bruce Dawson's analysis. A process held to a 32 MiB working set spent about 99% of sampled CPU in the page-fault path, and a 64 MiB scan ran roughly 250 to 800 times slower ([engineered.at summary](https://engineered.at/articles/32-mib-working-sets-on-a-64-gib-machine)). That is an extreme, single case, but it shows the direction of the harm. Mem Reduct's own README says results vary "roughly 10-50%" and that it relies on undocumented Native APIs whose behaviour may vary across Windows versions ([Mem Reduct GitHub](https://github.com/henrypp/memreduct)).

## What existing tools do, and what separates defensible from placebo

Mem Reduct is the only tool with auditable calls (GPL-3.0). It issues separate NtSetSystemInformation commands for empty working sets, system file cache, modified file cache, modified list, standby list, priority-0 standby, registry cache and combine pages. It deliberately masks the standby and modified items out of automatic runs unless the user opts in, applies a cooldown that references a "cleaning loop" bug, and refuses to clean when not elevated ([Mem Reduct main.c, read via a summarizing fetch, so re-verify against raw source](https://raw.githubusercontent.com/henrypp/memreduct/master/src/main.c)). Its numeric defaults were not visible in the fetch [Unverified]. Process Lasso's SmartTrim is the most conservative commercial design. According to Bitsum, it is off by default, checks every 15 minutes, acts only above 65% RAM load, trims only background processes with a working set above 196 MB, skips the active application and supports per-program exclusions. Its standby purge is off by default and fires only when free RAM excluding cache is below 1024 MB. Bitsum suggests 75% load, a 512 MB working-set minimum and a 2048 MB purge threshold for 32 GB machines, and says most PCs with 16 GB or more never need it ([Bitsum SmartTrim](https://bitsum.com/smarttrim/)). These are vendor claims, not independent measurements. ISLC (the gamer-oriented standby cleaner) purges only when both standby size and free memory cross thresholds. Its community defaults conflict (about 1 GB, with 1024 MB for 16 GB and 2048 MB for 32 GB), and some users report micro-freezes on each purge ([Wagnardsoft forum, search snippet](https://www.wagnardsoft.com/forums/viewtopic.php?p=6700)). Wise and CleanMem document no APIs or thresholds, so treat them as opaque. The CleanMem author states it "WILL NOT make your system faster" ([CleanMem](http://www.pcwintech.com/node/1697)).

The evidence for benefit is thin. The only support for standby purging is anecdotal. ISLC users report ending periodic game hitching, but the one example is confounded because the user also disabled DXR ([EA forum](https://forums.ea.com/discussions/battlefield-v-en/game-randomly-freezes-for-up-to-a-second/6638911/replies/6638936)). Anecdotes about Mem Reduct freezing for 20 seconds or more after cleaning the standby and modified lists, fixed by turning those options off, point the other way ([Tom's Hardware forum](https://forums.tomshardware.com/threads/my-computer-freezes-whenever-i-clean-the-standby-list.3704224)). One Microsoft Q&A case (64 GB machine, nearly all memory "Cached", mapped files held by a backup service) shows a real pathology that RAMMap's Empty commands did not clear. That points to fixing the offending application rather than cleaning ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4292425/cached-memory-slowing-performance-to-a-crawl?page=2)). My synthesis: plausible benefit exists in three narrow cases (a leaking or idle-but-huge background process, machines under 8 GB under real pressure, and a standby-related stall with low free memory), while periodic blanket trimming and repeated standby purges have plausible harm through refaults, cold caches, extra disk reads and CPU [Inference, not benchmarked]. The benefit of timer-based cleaning, "defragment memory", the registry-cache action and combine-pages is [Unverified]. No evidence on SSD wear from extra pagefile writes was found.

## Exact native APIs, rights and risks

The table separates the actions Toolboks should ship from the one it should gate. All rows are [Sourced] from Microsoft Learn unless marked. Undocumented items are marked.

|---|---|---|---|
| Per-process trim | `OpenProcess(PROCESS_SET_QUOTA \| PROCESS_QUERY_LIMITED_INFORMATION)` then `K32EmptyWorkingSet` (Win32::System::ProcessStatus), equivalent to `SetProcessWorkingSetSizeEx(h,-1,-1,0)` ([EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset)) | PROCESS_SET_QUOTA plus a query right; no admin needed for same-user non-protected processes (inference from the access-right docs) | Pages go to standby/modified and soft-fault back. Command numbers 0 to 6 are inferred from enum order; the NtDoc page does not state them ([NtDoc enum](https://ntdoc.m417z.com/system_memory_list_command)), so resolve and test them at runtime. May be monitored by security products [Unverified] |
| Not recommended | Same call with `MemoryEmptyWorkingSets` (2), `MemoryFlushModifiedList` (3), `MemoryPurgeStandbyList` (4) | Same | Empty-all trims every process. Flush-modified forces disk writes. Full purge drops all cached file data so the next access hits disk [Inference] |
| Do not use | Job objects (`JOB_OBJECT_LIMIT_WORKINGSET`, process/job memory limits) | Needs rights on the target, not verified | Commit limits cause allocation failures in other apps; KILL_ON_JOB_CLOSE can kill apps if the cleaner exits ([JOBOBJECT_BASIC_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)) |
| Not a RAM tool | EcoQoS via `ProcessPowerThrottling` | PROCESS_SET_INFORMATION | CPU/power policy only; documented to have no memory effect. Do not market it as RAM freeing ([SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)) |

To enable the privilege in Rust, call OpenProcessToken with TOKEN_ADJUST_PRIVILEGES and TOKEN_QUERY, LookupPrivilegeValueW for "SeProfileSingleProcessPrivilege", then AdjustTokenPrivileges, and check GetLastError for ERROR_NOT_ALL_ASSIGNED. Without the privilege, expect STATUS_PRIVILEGE_NOT_HELD (0xC0000061) [Inference, standard NT behaviour]. Treat access-denied on OpenProcess as a skip, never an error. Protected processes reject SET_QUOTA, SET_INFORMATION and QUERY_INFORMATION from other processes and allow only PROCESS_QUERY_LIMITED_INFORMATION ([MS Learn: Process Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights)). Anti-cheat drivers likely strip handle rights on game processes, which would make the open fail, and acting on a game could trip some anti-cheat [Inference, unsourced], so never open handles to games or the foreground process. The privilege to raise a working set above its current size (SE_INC_WORKING_SET_NAME) is generally held by all users, but Toolboks never needs it ([SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)). Whether Windows 11 24H2/25H2 changed any of these calls, and whether Defender or EDR flags them, was not found in any source [Unverified].

## When to act, what to skip, and how to act

No Microsoft numeric guidance for "Available below X" or a commit percentage exists in the notes. The thresholds below are tool defaults or my synthesis and should be treated as starting values to tune [Inference].

**Pressure detection.** Compute a "pressure" state only when at least two signals hold continuously for about 60 seconds. The signals are Available below max(10% of RAM, 1.5 GB), commit charge above about 85 to 90% of the commit limit, the system Low-memory notification signalled, Compressed growing, and elevated hard faults per second. Never act on "In use %" alone. For the Low-memory signal, `CreateMemoryResourceNotification(LowMemoryResourceNotification)` gives a system-wide waitable handle that needs no privilege; thresholds are OS-defined and not configurable, the handle stays signalled while the condition holds, and the range between low and high signals neither ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification)). A naive wait loop would therefore spin and re-clean, so always pair it with a cooldown. If commit is near the limit, do not clean. Advise closing the heaviest app or leaving the pagefile system-managed instead, because trimming cannot help.

**Cadence and hysteresis.** Evaluate every 5 to 15 minutes at most (SmartTrim uses 15). Allow at most one automatic run per hour. After a run, require pressure to clear (for example Available above 15% of RAM or 2 GB) before re-arming. Scale thresholds by RAM size, following Bitsum's 65% versus 75% split, rather than a fixed percent. Do not add "long uptime" triggers; no evidence supports them. Automatic mode defaults to off. Manual runs are always available but de-emphasised when memory is healthy.

**Eligibility filter for trims.** Apply every condition [Inference, assembled from SmartTrim's documented behaviour and API semantics]. The process is not the foreground window's process or its children, and has no recent input. It has been minimized or idle for several minutes, with CPU-time and I/O deltas near zero over a sampling window (GetProcessTimes, GetProcessIoCounters). It holds no active audio session and has no fullscreen or exclusive window, and its working set is at least about 200 MB (512 MB on large-RAM machines). It is not a game-launcher child. Skip System, Registry, MemCompression, services and anything that cannot be opened. Limit each process to one trim per 30 to 60 minutes, and skip any process whose working set regrew rapidly after its last trim, since that process was not idle. GetLastInputInfo is useful for idle detection, but it is session-specific and not guaranteed monotonic ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo)). Name lists of games and anti-cheat are brittle, and no credible source for them exists; prefer structural exclusions.

**Action ladder.** Report first. Second, set memory priority 2 (low) on eligible background processes, which is reversible and has no immediate cost. Third, trim eligible idle processes one at a time and sample faults afterward. Fourth, only on an explicit user click under real pressure, run the low-priority standby purge with a warning. For leaks, do not trim. Track per-process private bytes over 30 or more minutes and flag sustained growth (for example above 100 MB per hour without a plateau), then recommend restarting that named app. These leak thresholds are synthesis with no consumer-tool precedent found. Hibernation, Fast Startup and startup-app advice has no primary source in the notes, so omit it or mark it as general advice.

## Measuring and reporting the benefit honestly

Never display "freed X GB". Available counts standby, so a standby purge does not raise it, and a trim raises it only by moving pages to a list that Available already includes. MEMORYSTATUSEX's ullAvailPhys is standby plus free plus zero ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)). Take readings immediately before, immediately after, and again after a settle period of about 30 and 120 seconds [Inference, reasoned from transition-page mechanics]. The settle readings show whether the gain stuck or the memory was reloaded.

For system numbers, use `GetPerformanceInfo` (commit total, commit limit, physical available, system cache, kernel paged and nonpaged, all in pages) ([PERFORMANCE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information)). For per-process private working set and commit, use `GetProcessMemoryInfo` with `PROCESS_MEMORY_COUNTERS_EX2`, which requires Windows 10 22H2 or Windows 11 22H2 with the September 2023 cumulative update ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)). Read the exact zero+free, modified and standby-by-priority counts with a query on `SystemMemoryListInformation`. That query returns ZeroPageCount, FreePageCount, ModifiedPageCount and PageCountByPriority[8], in pages ([NtDoc](https://ntdoc.m417z.com/system_memory_list_information)). NtDoc notes the privilege only on the set path, but non-elevated query behaviour is [Unverified], so implement a fallback to the Memory\ performance counters (Modified Page List Bytes, Standby Cache Reserve, Normal Priority and Core bytes) ([MS Learn: Memory Performance Information](https://learn.microsoft.com/en-us/windows/win32/memory/memory-performance-information)). For rates, sample PDH `Memory\Page Faults/sec` and `Memory\Pages Input/sec` for 30 to 60 seconds after any action. Exact counter paths and definitions were not confirmed in the notes, so validate with `typeperf -q Memory` on the target [Unverified]. The Pages Input/sec description as hard-fault reads from disk is general knowledge, not sourced.

Wording rules for the run report: say "moved X GB from active use to cache", not "freed". Show the settle-period delta. If Available fell back or hard faults rose, say "memory was reloaded". Show commit unchanged, since it is the one figure a trim cannot move, and say why. Count processes touched, and show a run history. No published benchmark of app launch time, 1% lows or disk reads before and after cleaning exists in the notes [Unverified], so the page must not claim speed improvements. Toolboks can generate its own evidence cheaply by logging fault rates around each run and showing the user their own data.

## What the memory page should show and say

The design below is synthesis informed by Task Manager's layout and the Mem Reduct and SmartTrim designs; no formal UX source was found [Inference]. A commentator notes that Task Manager makes users interpret several numbers while macOS shows a single pressure graph ([Windows Latest](https://www.windowslatest.com/2026/11/05/windows-11-using-most-of-your-ram-microsoft-says-thats-a-good-thing-as-the-real-test-is-whether-your-pc-stays-responsive/)). A graph-first page with a plain verdict fills that gap.

The top of the page is a one-sentence verdict with a three-state indicator (Healthy, Busy, Under pressure) driven by the pressure rules above. The default text is: "Memory looks healthy. Windows is using spare RAM as a cache, which is normal." Below it sits a composition bar (In use, Modified, Standby cache, Free, with Compressed noted), a separate commit bar (used versus limit), and a short rolling history of Available, commit and hard faults per second. A top-consumers table shows private bytes and working set, the one-hour growth slope, and a state (foreground, background, idle), each with a concrete suggestion (restart this app, close the duplicate browser, lower priority). Windows labels in Task Manager are only documented in secondary sources, so keep Toolboks's own labels plain and avoid reusing Task Manager's terms in ways that might mislead ([HelpDeskGeek](https://helpdeskgeek.com/task-manager-ram-meaning-explained/)).

The primary action is labelled honestly, for example "Trim idle background apps". It is de-emphasised or disabled when memory is healthy, with the sub-line "Moves unused memory to cache. May cause brief reloads. Does not reduce commit." The low-priority standby purge sits under Advanced, requires elevation, and carries a warning that it discards cached files and may cause brief disk reads. Settings include auto-clean (off by default), a pressure-only toggle, thresholds scaled to RAM size, an exclusion list, cooldown, and a display of the exact rule that triggered each automatic run. Warnings cover games, low-RAM systems, and commit near the limit (advise closing apps or leaving the pagefile system-managed, since a system-managed pagefile is standard advice per [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2263659/how-does-windows-11-handle-memory-management), a secondary source). Never promise speed.

## Conclusion

The research reframes the product question. A RAM cleaner on Windows 11 cannot add memory the OS would not already hand out, so its honest value is diagnosis, plus targeted relief when one process or a cache stall is the real problem. The most useful single feature is probably not an action at all but a clear pressure verdict that tells most users with 16 GB or more that nothing is wrong, which is what Bitsum itself tells its own users.

Confidence is uneven. The page-list mechanics, access rights, memory-priority API, commit-limit behaviour and measurement APIs are well sourced. The thresholds, cooldowns, eligibility filters, leak slopes and UI design are my synthesis. The following remain unverified: the benefit or harm of any action in controlled tests, Windows 11 24H2/25H2 behaviour changes, non-elevated query behaviour of the memory-list class, undocumented command numbers, Defender and anti-cheat reactions, the content of Russinovich's article, and the numeric defaults of Mem Reduct, ISLC and Wise. Before release, run a small internal benchmark (launch time, hard faults and Pages Input/sec, game frame times) on a 8 GB and a 16 GB machine, and let the results decide whether the trim and purge actions stay in the product.
